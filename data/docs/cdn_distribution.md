# CDN 视频分发详解

## CDN 架构概述

CDN（Content Delivery Network，内容分发网络）是由分布在不同地理位置的边缘服务器组成的分布式网络，通过将内容缓存到距离用户最近的节点来降低延迟、提升传输速度、减轻源站压力。

### 核心层级结构

```
用户
  ↓  就近访问
边缘节点（Edge Node / PoP）  ← 命中缓存直接返回
  ↓  缓存未命中
二级节点（Mid-tier / L2）    ← 区域聚合层
  ↓  仍未命中
源站（Origin Server）        ← 真实内容存储
```

- **边缘节点（Edge Node / PoP）**：直接面向用户，部署在城市级网络接入点，全球可达数千个
- **二级节点（Mid-tier）**：区域汇聚层，减少回源压力，部分 CDN 采用三层架构
- **源站（Origin）**：视频文件的原始存储位置（对象存储或流媒体服务器）

---

## 边缘节点与回源（Origin Pull）

### 缓存命中流程

```
1. 用户请求 video.mp4
2. DNS 解析 → GSLB → 分配最近边缘节点 IP
3. 边缘节点查找本地缓存
   ├── 命中（Cache Hit）→ 直接返回，响应时间 <10ms
   └── 未命中（Cache Miss）→ 向上级节点或源站回源
4. 回源获取内容后，缓存到边缘节点
5. 返回给用户，同时刷新缓存 TTL
```

### 回源策略

- **懒加载（Lazy Pull）**：首次请求时才回源，适合长尾内容
- **预热（Pre-warm）**：发布前主动将热门内容推送到边缘节点，消除首次请求的回源延迟
- **回源鉴权**：边缘节点回源时携带签名或 Token，防止源站被直接访问

## 缓存策略

### Cache-Control 指令

```http
Cache-Control: public, max-age=86400      # 缓存 1 天
Cache-Control: no-cache                   # 每次需向源站验证
Cache-Control: no-store                   # 不缓存（付费内容）
Cache-Control: s-maxage=3600             # CDN 缓存时间（覆盖 max-age）
```

### TTL 设计

| 内容类型 | 推荐 TTL | 原因 |
|----------|----------|------|
| 视频切片（.ts / .m4s） | 7~30 天 | 内容不变，URL 含版本信息 |
| M3U8 媒体播放列表（VOD） | 1~7 天 | 内容固定 |
| M3U8 直播播放列表 | 2~5 秒 | 频繁更新 |
| MPD（VOD） | 1~7 天 | 内容固定 |
| 封面图 | 1~7 天 | 偶尔更新 |
| 带签名 URL 的资源 | URL TTL | 签名过期即失效 |

### 缓存键（Cache Key）设计

缓存键决定哪些请求共享同一缓存条目。默认缓存键通常是完整 URL（含 Query String）。

**视频场景优化**：

- 将签名参数（`token`, `expires`, `sign`）从缓存键中剥离，避免每个用户的签名 URL 产生独立缓存
- 保留内容标识参数（`vid`, `quality`）
- 示例：`https://cdn.example.com/video/123/720p/seg001.ts?sign=abc&t=1234` → 缓存键剥离 `sign` 和 `t`

## 视频 CDN 特殊性

### Range Request（范围请求）

视频播放器通过 HTTP Range 请求下载文件的特定字节范围，支持快进/跳转：

```http
# 请求
GET /video.mp4 HTTP/1.1
Range: bytes=1048576-2097151

# 响应
HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-2097151/104857600
Content-Length: 1048576
```

CDN 处理 Range 请求时：
- 如果缓存了完整文件，直接切割返回
- 如果未缓存，回源时同样使用 Range 请求（避免拉取整个大文件）
- **分片缓存（Slice Cache）**：将大文件切成固定大小（如 1MB）分别缓存，提升缓存利用率

### 分片预取（Prefetch）

边缘节点在用户当前播放位置之前主动预取后续切片：

- 减少客户端等待时间
- 提升缓存命中率（后续用户请求直接命中）
- 直播场景：边缘节点订阅新切片，可用时立即缓存

## 推流 vs 拉流

| 特性 | 推流（Push） | 拉流（Pull） |
|------|------------|------------|
| 发起方 | 内容源主动推送到 CDN | CDN 向内容源拉取 |
| 协议 | RTMP、SRT、WebRTC | HTTP、HLS、RTMP |
| 延迟 | 低（实时传输） | 高（缓存+拉取） |
| 典型场景 | 直播推流（OBS → 直播平台） | 点播分发、CDN 回源 |
| 带宽利用 | 固定占用推流带宽 | 按需拉取，节省带宽 |

## CDN 调度策略（GSLB）

GSLB（Global Server Load Balancing，全局服务器负载均衡）负责将用户请求路由到最优边缘节点。

### 就近接入

- **DNS 调度**：根据用户 LocalDNS 的 IP 地址判断地理位置，返回最近边缘节点的 IP
  - 优点：简单、通用
  - 缺点：DNS 缓存导致调度不及时，LocalDNS 不代表用户真实位置
- **HttpDNS**：APP 直接向 GSLB HTTP 接口查询，携带用户真实 IP，返回最优节点 IP
  - 优点：精准、实时
  - 缺点：需要客户端集成 SDK

### 调度维度

1. **地理位置**：优先选择物理距离近的节点
2. **网络质量**：RTT、丢包率（通过探测获取）
3. **节点负载**：CPU、带宽、连接数
4. **运营商**：同运营商节点优先，避免跨网延迟（电信用户 → 电信 CDN 节点）

## 视频直播分发链路

```
推流端（OBS / 手机 APP）
  ↓  RTMP/SRT 推流
直播推流源站（Ingest Server）
  ↓  转封装 RTMP → HLS/DASH（传码）
直播转码集群（多码率转码，可选）
  ↓  HLS 切片写入存储
CDN 源站（Origin Pull Point）
  ↓  边缘节点回源订阅
CDN 边缘节点（全国/全球分布）
  ↓  HTTP 分发
播放端（APP / Web）
```

**关键时延组成**：
- 采集编码延迟：50~200ms
- 推流网络延迟：100~500ms
- 转封装延迟：切片时长（通常 2~6s）
- CDN 传播延迟：100~500ms
- 播放器缓冲：2~10s

## 关键指标与优化

### 首帧时间（TTFF，Time To First Frame）

从用户点击播放到画面出现的时间，是用户体验的核心指标。

**优化手段**：
- CDN 节点预热（热门内容提前缓存）
- 减小 Initialization Segment 大小
- HTTP/2 多路复用减少连接建立开销
- 就近接入降低网络延迟
- 播放器端：预加载（Preload）、预缓冲

**行业基准**：移动端 TTFF < 1 秒为优秀，> 3 秒用户大量流失。

### 卡顿率（Buffering Ratio）

卡顿时间占总播放时间的比率：

```
卡顿率 = Σ(缓冲等待时间) / 总播放时间 × 100%
```

**优化手段**：
- ABR 算法优化（避免过激的高码率选择）
- 增大初始缓冲区
- CDN 节点带宽提升
- 弱网场景降级至低码率

### 常见监控指标

| 指标 | 说明 | 目标值 |
|------|------|--------|
| TTFF | 首帧时间 | < 1s |
| 卡顿率 | Buffering Ratio | < 0.5% |
| 缓存命中率 | Cache Hit Ratio | > 95% |
| 回源带宽 | Origin Bandwidth | 尽量低 |
| 错误率 | HTTP 5xx 比例 | < 0.1% |
| P95 下载速度 | 95th 百分位下载速度 | > 目标码率 3x |
